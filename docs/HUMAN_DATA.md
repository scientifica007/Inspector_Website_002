# حماية البيانات بعد بدء الاختبار البشري

الحالة عند البناء: بيانات محلية تجريبية فقط؛ لم تُسلَّم موافقة على تغيير بيانات قبول بشري فعلية.
بمجرد إعلان المالك أنه بدأ إدخال بيانات فعلية، تصبح الخطوات التالية إلزامية لأي Data Migration مهمة أو عملية مدمرة:

1. قراءة حالة الفرع/HEAD والمخطط وقاعدة البيانات الفعلية، دون نشر بيانات شخصية.
2. تحديد الجداول والحقول والسجلات التي ستتغير، وأثرها التاريخي.
3. عرض المخاطر والبديل غير المدمر.
4. تحديد rollback واقعي؛ migration عكسية وحدها لا تسترجع قيمًا حُذفت.
5. إنشاء Backup خارج المستودع العام وفي مكان آمن دائم.
6. التحقق من Backup بفتح نسخة معزولة وفحص سلامتها وأعداد السجلات واسترجاع عينة صادرات.
7. الحصول على موافقة المالك الصريحة على التغيير المحدد بعد عرض الأدلة.
8. التنفيذ في نافذة متفق عليها، مع إيقاف الكتابات أو آلية تعزلها.
9. Readback وQA ثم مقارنة السجلات والصادرات المتأثرة بالنسخ قبل التنفيذ.
10. تسجيل النتيجة وموضع النسخة الاحتياطية دون أسرار أو بيانات شخصية في GitHub.

SQLite: استخدم Python `sqlite3.Connection.backup` أو أمر SQLite backup، وليس نسخ ملف قاعدة نشطة وإهمال WAL.
اختبار `PRAGMA integrity_check` يجب أن يعطي `ok`، وتُجرّب الاستعادة إلى مسار مستقل.
PostgreSQL: استخدم `pg_dump` ثم تجربة `pg_restore` في قاعدة منفصلة. لا تعِد توجيه التطبيق إلى النسخة الأصلية أثناء الاختبار.

حراس التاريخ في migration 0002 جزء من سلامة البيانات. إذا تطلب تعديل مخطط SQLite إعادة إنشاء جدول محمي،
يجب إعادة تثبيت حراسه وفحص وجودها قبل إعادة فتح الكتابات. لا تُحذف الحراس لتجاوز خطأ في منطق التطبيق.
الاحتفاظ بالنسخة السابقة من Git لا يكفي وحده لاسترجاع بيانات قاعدة البيانات.
